# CIP-0002: Material review: chapters, talks, and snippet freshness

## Status

- [x] Proposed - Initial idea documented
- [x] Accepted - Approved, ready to start work
- [x] In Progress - Actively being implemented
- [ ] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete
- [ ] Rejected

## Summary

Create a repeatable **material review** process for ExecEd that checks:

- course lectures (`execed/_lamd/*.md`) against *The Atomic Human* chapter themes (`~/lawrennd/the-atomic-human/_chapters/`)
- coverage and evolution in recent talks (especially `~/lawrennd/talks/_atomic-human/` and `~/lawrennd/talks/_business/` and `~/lawrennd/talks/_policy/` and `~/lawrennd/talks/_economics/`)
- the “freshness” of the snippets we rely on (last change date + where they are used), and proposes a prioritised refresh list.

## Motivation

Now that CIP-0001 has reframed Sessions 1–7, we need a disciplined way to keep the course coherent as:

- new talks introduce better “canonical spines”
- snippets drift (or accrue better examples/figures)
- chapter framing evolves (or we discover gaps/misalignments between chapter intent and lecture delivery)

Without a review loop, the course will regress into ad-hoc patching.

## Detailed Description

### Inputs (sources to audit)

- **Course lecture sources**: `execed/_lamd/*.md`
- **Course generated outputs** (sanity check only): `execed/_lectures/`, `execed/slides/`
- **Book chapters**: `~/lawrennd/the-atomic-human/_chapters/`
- **Talk sources**:
  - Primary: `~/lawrennd/talks/_atomic-human/`, `~/lawrennd/talks/_business/`
  - Secondary as needed: `~/lawrennd/talks/_ai/`, `~/lawrennd/talks/_policy/`, `~/lawrennd/talks/_governance/`
- **Snippet library**: `~/lawrennd/snippets/**/includes/*.md`

### Review questions (what “good” looks like)

- **Coverage**: For each ExecEd session, do we have:
  - a clear chapter anchor (or explicit “not chapter-aligned” rationale),
  - at least one recent-talk spine that supports the same message,
  - and a stable set of canonical snippets?
- **Consistency**: Are we telling the same story across:
  - the course abstract/title,
  - the included snippets (lecture body),
  - and the examples we surface from recent talks?
- **Freshness & drift**:
  - Which snippets are heavily used (in ExecEd + recent talks)?
  - Which are stale (no changes for a long time) but high-impact?
  - Which are actively changing and might need re-stabilising (or pinning)?

### Outputs (deliverables)

- A material review report (human-readable), containing:
  - **Session-by-session “coverage + gaps”** table
  - a **top snippets list** (frequency) across ExecEd + recent talks
  - a **staleness list** (snippet last update date via git history)
  - a **refresh candidate list** (prioritized, with rationale)
- A set of backlog tasks to perform the refresh work (scoped, testable).
- A reusable **tooling layer** (scripts/CLI) so the same questions can be asked repeatedly and shared with others.

### Tooling proposal (long-term integration with `lamd`)

This CIP proposes that the inventory checks become **reusable tooling** rather than one-off analysis.

- **Goal**: provide commands that others can run (in ExecEd and other courses/talk repos) to answer:
  - “Which snippets does this course use?”
  - “Which talks use these snippets (since date X)?”
  - “Which snippets are stale/high-impact and should be refreshed?”
  - “Which sessions lack coverage for key chapter themes?”
- **Approach**:
  - Implement first as small, documented scripts in `execed/scripts/` (so we can iterate quickly).
  - Upstream (or mirror) as `lamd` tooling once stable (e.g. a `lamd` subcommand or a small `lamd` helper CLI).
  - Prefer machine-readable outputs (JSON/CSV) plus a human report so the results can be used in CI, docs, or other automation.

## Implementation Plan

1. **Build an inventory of ExecEd snippet usage**
   - Parse `execed/_lamd/*.md` for `\\include{...}` statements.
   - Produce `session → includes[]` and `include → sessions[]`.

2. **Build an inventory of recent talk usage**
   - Choose a cutoff date (default: `2024-06-01`) and a scope:
     - required: `_atomic-human`, `_business`
     - optional: `_ai`, `_policy`, `_governance`
   - Parse talk sources for `\\include{...}` statements.
   - Produce `include → talks[]` and `talk → includes[]`.

3. **Compute snippet “freshness”**
   - For each snippet path referenced above:
     - find last modification date from git history (preferred: `git log -1 --format=%cs -- <path>`)
     - capture a short last-commit message for context.
   - Flag “stale” snippets using a configurable threshold (e.g. > 12 months).

4. **Cross-check against chapters**
   - For each session:
     - list its intended chapter anchors (from CIP-0001 / session plans)
     - skim chapter headings/takeaways to confirm alignment
     - list “missing but relevant” chapter points not reflected in the session.

5. **Produce recommendations**
   - Prioritise by:
     - session importance (core pathway),
     - snippet usage frequency,
     - snippet staleness,
     - and risk (does drift affect trust/accountability messaging?).
   - Recommend either:
     - refresh snippet content,
     - swap to a newer canonical snippet,
     - or add a new snippet (only if clearly needed).

6. **Translate into backlog tasks**
   - Create tasks for:
     - snippet refresh (edit snippets + recompile affected lectures),
     - lecture refresh (when a lecture needs new spines),
     - and asset alignment (figures/featured images).

7. **Package the review as reusable tooling**
   - Add scripts (initially in `execed/scripts/`) that generate:
     - snippet usage inventory for a target directory
     - talk usage inventory since a cutoff date
     - snippet freshness report (last git change + message)
     - summary report (markdown) + machine-readable output (JSON/CSV)
   - Document expected inputs/outputs and how to run them.
   - Identify the pieces suitable for upstreaming to `lamd` (long-term integration).

## Backward Compatibility

- No requirement to preserve legacy redirects; course framing changes are allowed.
- Any snippet changes must be checked by rebuilding the ExecEd lecture set.

## Testing Strategy

- Run `execed/_lamd/compile.sh` after any snippet/lecture change.
- Spot-check at least:
  - one lecture page and one slide deck for each modified session
  - rendered figures and citations for any modified snippet
